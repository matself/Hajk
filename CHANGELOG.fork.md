# Fork changelog

Changes specific to this fork ([matself/Hajk](https://github.com/matself/Hajk)) that are not part of upstream [hajkmap/Hajk](https://github.com/hajkmap/Hajk). `CHANGELOG.md` mirrors upstream's changelog so it can be diffed/merged cleanly against `upstream/develop`; entries here won't appear there and are not intended to be upstreamed.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [unreleased]

### Breaking

- Client + Admin: Bookmarks/LayerSwitcher - Split the overlapping "save current state locally" concepts into two strictly-scoped ones: Bookmarks (renamed "Platser" in the UI) now saves only the map's position (center + zoom) and no longer restores layer visibility, opacity, draw order or background; LayerSwitcher's "Mina favoriter" (renamed "Mina teman") and the admin-defined "Teman" (relabeled "Färdiga teman") remain layer-only and unaffected. A map that previously relied on Bookmarks alone to persist a layer combination now needs "Mina teman" enabled as well. No data migration needed - existing saved bookmarks simply ignore their now-unused layer fields.

### Added

- Backend: New `npm run check-belagenhetsadress` diagnoses access to Lantmäteriet's Belägenhetsadress Direkt from the command line, because a 403 from that API is genuinely ambiguous: the gateway answers code `900910` when a token is real and the subscription valid but the token's scope does not cover the endpoint, and entitlements can differ per group of operations. The script prints the token's scope, issuer and expiry (decoding the JWT locally, so nothing is pasted into a web tool), then calls one endpoint from each group - health, autocomplete, referens, punkt - and says which answered. It ends with the reading: everything refused points at a token minted without a scope or belonging to the other environment, while a mixed result is per-operation scoping and means either asking Lantmäteriet for the missing scope or pointing the plugin at a group that works. When the reference search does answer it also prints the first result verbatim, which is the only way to see the field names for a response whose schema is not published outside Geotorget.
- Client: AddressSearch - An error from the address service now reaches the user with the service's own words instead of "kontrollera token". The two services answering on that route both explain themselves in the response body - Lantmäteriet's `Fault` object and, in front of it, the API gateway's `{code, message, description}` - and the difference matters: a gateway `900910` means the token is genuine but its scope does not cover the endpoint, which is a different problem from a wrong or expired token and sends you looking in a different place. HTML error pages from something further out are still suppressed, since a page of markup in a snackbar helps nobody.
- Client + Admin: AddressSearch plugin - New client plugin ("Adressök") searches Swedish addresses in Lantmäteriet's Belägenhetsadress Direkt and moves the map to the one picked, with a marker. Results appear while typing, debounced, and the debounce is configurable because each search is a call against Lantmäteriet. A second button turns the map into an address picker: click anywhere and the nearest address is fetched and filled in. Searching is deliberately two calls, because the API separates label from geometry - `referens/fritext` returns references while typing, and only the address actually chosen is fetched in full - so keystrokes stay cheap. Configurable per map in Admin: token, max hits, debounce, kommunkod, zoom level, whether reserved addresses are included and whether the map picker is offered. Note that the API speaks SWEREF 99 only, so the plugin asks for the map's own projection when it is one of EPSG:3006-3018 and otherwise falls back to EPSG:3006 and transforms - which needs EPSG:3006 present under `projections` in the map config, and says so plainly when it is missing. Verified in a browser against a stubbed API: a Gävle address in EPSG:3006 lands the map within 50 cm of the independently computed EPSG:3857 position, 17 keystrokes collapse into one search call, and the map-click lookup sends northing before easting as the API requires - the reverse of OpenLayers' own order, and the easiest thing to get silently wrong here.
- Backend: Lantmäteriet Belägenhetsadress Direkt - New server-side proxy (`/api/v2/belagenhetsadressproxy`, enabled with `LANTMATERIET_BELAGENHETSADRESS_ACTIVE`) that forwards address lookups to Lantmäteriet's Belägenhetsadress Direkt API and attaches the subscription's bearer token. The product is free of charge but access is granted per organization under Lantmäteriet's terms, so the token stands for someone's approved use rather than for a bill - and the proxy is also what avoids the CORS wall a browser hits calling the API directly. The token can sit in either of two places: set `LANTMATERIET_BELAGENHETSADRESS_TOKEN` in `.env` and it never reaches the browser, which is what to prefer when you can edit that file; leave it unset and the proxy forwards the Authorization header the client sends instead, which is where a token configured per map in Admin arrives from - the same arrangement as the Markhöjd proxy. Note that the route forwards any path below the product's base URL to anyone who can reach the backend, so a publicly exposed instance should restrict it at the reverse proxy or by network. The middleware deliberately omits the `pathRewrite` block its neighbours carry: Express strips the mount path before the middleware sees the request, so that block never matched and returned `undefined` - harmless, since the default path handling resolves the URL correctly, but it logged a misleading `~> undefined` for every request.
- Admin: Disabled the Sorteringsordning field on the three tools where it does nothing - Genvägar (`preset`), Externa kartlänkar (`externalLinks`) and Om kartan (`information`) - with a short note next to it saying the button has a fixed position. All three are drawn as hardcoded control buttons in the client's `App.jsx` and never reach the plugin manager that sorts on `index`, so the control was offering an ordering that could not happen. The stored value is left untouched: each form still reads `tool.index` into state on mount and writes `this.state.index` back on save, so nothing is rewritten or lost, and the field stays visible so the configuration remains legible.
- Admin: Renamed the "Externa länkar" tool to "Externa kartlänkar" in the tool list. The old name said nothing about what the links point at, and read as generic web links rather than what the tool actually does, which is hand the map's current position to another map service. Display name only - the codename `externalLinks` is unchanged, so existing map configs are unaffected.
- Docs: Corrected what `admin-tooloptions.md` says about **Sorteringsordning**, which was misleading in two ways. It now explains that `index` is a single global number whose effect is per container - the client sorts every tool into one list and mounts them in that order, after which each tool puts its button in its own container, so only relative order within a container is ever visible and equal values in one container fall back to plugin load order. It also records three tools where the field does nothing at all: `preset`, `externalLinks` and `information` are drawn as fixed control buttons in `App.jsx` and never reach the plugin manager, having kept their tool configuration when they were converted from plugins to built-in controls. Noted too that the Drawer's own toggle buttons sort by a separate `order` property unrelated to `index`, and that even where `index` works, plugin control buttons all land in one fixed slot mid-column and cannot be moved past the hardcoded ones. The three affected tool guides now carry the same warning.
- Admin: Externa kartlänkar - Rewrote the syntax help shown behind "Visa exempel". It previously offered three cryptic lines that never said what the placeholders were for: "x eller y = koordinat från kartan" does not convey that you write an ordinary URL and drop placeholders into it, or that the value substituted is the map's centre point at the moment the user clicks. The panel now opens with a sentence stating exactly that, distinguishes x as easting from y as northing rather than lumping them together, names SWEREF 99 TM as the projection an installation is most likely to want, and documents `{zoom}` - which the client has always substituted but the help text never mentioned. Also drops the stray English "optional" from the Swedish UI.
- Admin: Externa kartlänkar - Added Lantmäteriet "Min karta", Hitta.se and Eniro to the tool's built-in link examples, so they can be added with one click alongside the existing Google Maps/Street View and OpenStreetMap entries. The three shipped examples had all become largely redundant - Street View and Mapillary are embedded viewers inside Hajk and OSM is reachable through OsmSearch - which left the tool looking pointless despite its actual purpose being to hand the current map position to a site that cannot be embedded. Min karta is exactly that case. The example uses SWEREF 99 TM directly (`{x|EPSG:3006|0}`) with zero decimals, matching the integer easting/northing Min karta's own share links use, and pins `z` rather than interpolating `{zoom}` since the two applications' zoom scales do not correspond. Note that the target map config must list EPSG:3006 in its `projections` for the transform to resolve. Hitta.se and Eniro take WGS84 with latitude before longitude, the reverse of Min karta's easting/northing order. All three templates were verified against the live services rather than assumed: Eniro's was confirmed canonical by round-tripping its own "Kopiera länk" shortlink, which redirects back to the same `?c=lat,lon&z=` form, and Hitta's was confirmed by measuring its scale bar against the cosine-of-latitude prediction, since it exposes no share function and its server-rendered state always reports an IP-geolocated position regardless of the URL.
- Docs: New manual page `docs/admin-tool-externallinks.md` ("Externa kartlänkar") - the tool had no guide at all, only a row in the tool-list table, despite having the least self-evident configuration syntax of any tool in Admin. Covers the `{x|EPSG:xxxx|decimals}` and `{zoom}` placeholders, the fact that it sends the map centre rather than a clicked point, and three things that are otherwise only discoverable by reading the source: the `title` option exists but has no field in the form, `visibleAtStart` is read but never written back, and an unregistered projection fails silently with nothing but a console warning because the transform error is swallowed. It also documents the verified Hitta.se and Eniro templates, their latitude-before-longitude order, and one silent trap: `/kartan/flygfoto` on Hitta.se is not a real mode - the page loads, the coordinates are honoured, and you get the ordinary map with no error, so a mode name must be confirmed by the page title changing before it is trusted. It also notes that both Hitta.se and Eniro open with a partially incomplete interface, since the templates are the minimal link form that carries a position while the services' own links include further path segments that initialise the rest of the UI - cosmetic, and not a configuration error to go hunting for. Linked from the tool-list overview, whose audit date is bumped accordingly.
- Admin: WMS-lager - The "Tillgängliga lager" list in the WMS layer form can now be filtered and sorted. A GeoServer routinely publishes several hundred layers and the list reproduced the capabilities document verbatim, so finding a layer meant scrolling a 600-pixel-tall box in whatever order the server happened to use. A filter field matches on title or name (with a "visar X av Y" counter), and the Titel/Namn column headers toggle ascending/descending sorting. Sorting is applied per level so a group layer keeps its sublayers directly beneath it, and filtering still finds a sublayer whose parent group does not match. Neither affects the selection: layers already checked stay checked and remain listed under "Valda lager" while filtered out of view. Rows also got stable React keys, since the previous per-render guids re-mounted every row on each keystroke.
- Docs: New manual page `docs/admin-announcements.md` ("Meddelanden vid kartstart") documenting the `announcements` array in the client's `appConfig.json` - a startup snackbar with no Admin form at all, and therefore effectively undiscoverable. Covers every field, the four filters an entry must pass, the silent-failure modes (an invalid `maps` value or a non-numeric `timeout` change the behaviour with no error), and how `showOnlyOnce` remembers via `localStorage` - which is why editing the text of an already-shown entry has no effect unless its `id` changes. It also clears up the natural misreading that the array is a per-map message slot: the list is instance-wide and each entry names the maps it applies to. Cross-linked from the InfoDialog guide and the tool-list overview, since InfoDialog is the per-map, Admin-editable alternative.
- Admin: The tool list is now filtered by a `hiddenTools` array in the `mapsettings` section of `public/config.json`, so an installation can drop tools it has no use for without touching any tool code. Upstream's only way to hide a tool is to comment out its import, its `switch` case and its label in `tooloptions.jsx` - three edits per tool, a merge conflict on every upstream sync, and a rebuild to change your mind. The filter is four lines in one file, the hidden tools keep their source and their admin forms for reference, and the list is a config edit rather than a build. Note that hiding a tool does not disable it in map configs that already enable it: such a tool keeps working in the client but can no longer be switched off from Admin, so clear it from the maps first.
- Docs: New manual page `docs/admin-hidden-tools.md` ("Dölja verktyg i Admin"), covering how the `hiddenTools` filter works, which tools this edition hides and why, the two-file procedure for bringing one back (admin `config.json` plus the client's `availableTools`, with their differing lower/CamelCase conventions), the fact that hiding a tool does not disable it in maps that already use it, and how all this differs from upstream's commented-out plugins which still need a code edit and a rebuild. It appears in the Admin Manual tab automatically, and `admin-tooloptions.md` now marks the hidden tools in its overview table and links to the new page.
- Community edition: This experimental fork targets private and community users rather than municipalities, so tools that need a commercial licence, a paid account or municipal backend infrastructure are hidden by default. `hiddenTools` in the admin config holds `buffer`, `collector`, `dummy`, `edit`, `fmeserver`, `sketch` and `timeslider`; the client's `availableTools` in `appConfig.json` drops the same set plus `PropertyChecker`, which is municipality-specific and has no admin form at all. Nothing is deleted - every plugin remains in the source tree, and both lists are plain config that can be restored. The default `map_1.json` template had `buffer` and `sketch` enabled and no longer does, since a hidden-but-active tool cannot be turned off through the GUI.
- Client + Admin: Renamed the "Snabbval" control/tool to "Genvägar" — pure rename, no behavior change. The old name was too close to LayerSwitcher's "Snabbåtkomst" despite the two being unrelated mechanisms (admin-authored place+layer links vs. the quick-access layer group).
- Client + Admin: Renamed LayerSwitcher's "Snabbåtkomst" group to "Teman" — pure rename, no behavior change. Aligns the group's own name with the two theme types it already holds ("Färdiga teman" and "Mina teman"), instead of using an unrelated third term for the container itself. Updated the client UI, the guided tour, Admin's map settings form and default info texts, and the corresponding docs/wiki pages.
- Client: Platser + Mina teman - Both now tag what they save with the map config file they were saved from (`mapConfigName`/`m`). If a saved place or theme is later encountered under a different map (most likely after importing a file exported elsewhere), it's shown with a warning-colored label naming the original map, both in the list views and when loading it from the quick menu, instead of silently mixing it in.
- Admin: Manual - Added an in-app "Manual" tab that renders the `docs/admin-*.md` guides directly, mirrored into `public/manual/` at build time (`scripts/sync-manual.js`, wired into `prestart`/`prebuild`) so `docs/*.md` stays the single edited source with no separate HTML build step. Internal cross-links between guides (including ones with `#heading` fragments, and links out to non-`admin-*` docs like `deprecated-plugins.md`) resolve inside the viewer instead of navigating away - the failure mode Document Handler couldn't avoid, since its chapter model has no stable, linkable identity per chapter. Each doc gets its own bookmarkable URL (e.g. `#!/manual/admin-tool-search.md`, independent of whatever admin tab/tool is otherwise open) via a generic wildcard sub-route, and a full-text search box filters across all mirrored docs with match snippets, not just titles.
- Client + Admin: OsmSearch plugin - New client plugin lets users search for places via the OSM Nominatim geocoding API; the map zooms/pans to the selected result with a marker dropped at its location. Configurable in the admin GUI (search endpoint, result limit, country-code filter, bounding-box zoom toggle).
- Backend + Admin: Authenticated WMTS layers - WMTS services that require Basic authentication (e.g. Lantmäteriet Geotorget) can now be configured entirely in the admin GUI, with no external reverse proxy. Per-layer credentials are stored in the layers store and injected server-side by a built-in tile proxy (`/api/v2/wmtsproxy/:layerId`), so they never reach the browser and tiles load same-origin as ordinary images. The credentials are stripped from the client-facing map config. When credentials are supplied, the admin's WMTS "Hämta" (GetCapabilities) request is routed through the backend, which fetches server-side and handles the authentication and CORS that a browser fetch cannot.
- Backend + Admin: Map config backups - Every write to a map config or the layers store now snapshots the previous version first (before overwrite, delete, or restore). A configurable number of backups is kept per file (`MAP_CONFIG_BACKUP_COUNT`, default 100). A new "Säkerhetskopior" button in the admin "Kartor" toolbar opens a dedicated page listing the selected map's backups, where any version can be previewed and restored; restoring snapshots the current version first so it is itself reversible.
- Backend: Native single-password protection for `/admin` - a lightweight, AD-free alternative for deployments without Active Directory. A single shared password (`ADMIN_PASSWORD_HASH` in `.env`, generated via `npm run hash-admin-password`) gates both the admin UI and its API (`mapconfig`, `settings`, `ad`) behind a signed, 6-hour session cookie. Only engages when `AD_LOOKUP_ACTIVE` is off, so AD-based deployments are unaffected. See [commit](https://github.com/matself/Hajk/commit/d7784672dd53090babf29ee37c0ee0f13e495f34).
- Client + Admin: LayerSwitcher - Added XYZ as a configurable layer type, replacing the hard-coded `enableOSM` background approach. Any XYZ/slippy tile service (OpenStreetMap, OpenTopoMap, ESRI imagery etc.) can now be added and managed via the admin layer GUI. [#1866](https://github.com/hajkmap/Hajk/discussions/1866)
- Admin: InfoDialog - Added an admin editor for the `infodialog` tool (used for e.g. "Visa hjälp" and "Visa nyheter"), supporting multiple named dialog instances with add/remove/edit, a rich-text (HTML) editor by default for new dialogs, and a Markdown-source fallback for dialogs already saved in that format. [#1735](https://github.com/hajkmap/Hajk/issues/1735)
- Client: LayerSwitcher - The zoom-visibility warning snackbar (shown when a toggled layer is outside its configured min/max zoom) now has a "Zooma till synlig skala" button that zooms the map to the nearest zoom level where the layer becomes visible, in addition to the existing close button.
- Client + Admin: Added a new MailForm plugin - a lightweight alternative to Collector for sites that just want a "Tyck till" feedback form emailed instead of written to a WFS-T database. Users fill in their e-mail address and a free-text message; a link to the current map view is generated automatically. Submitting builds a `mailto:` link and hands off to the user's own mail client, so no backend mail server is required. Configurable via the Admin tool page (recipient address, subject, instructions).
- Admin: Infoklick - The "Inforuta" HTML template field for WMS and Vector layers is now a WYSIWYG editor (reusing the existing Draft.js dependency) instead of a plain textarea, with a "Hämta attribut" button that fetches the layer's actual attribute names (via `DescribeFeatureType` against the already-configured service URL) into an "Infoga attribut" picker, so templates can be built without guessing placeholder names. `{attribut}`-style placeholders are protected as atomic tokens that formatting can't split. Content containing `{{if}}...{{/if}}` conditional blocks automatically falls back to a raw "Kod" mode, since such blocks may embed arbitrary HTML that a WYSIWYG round-trip could corrupt.
- Client + Admin: Added a new Mapillary plugin - lets users click the map to view the nearest street-level Mapillary image in a resizable window, with a rotating marker on the map tracking the image's position/heading (including when navigating inside the viewer itself). Uses the Mapillary Graph API to search a configurable radius around the click (falling back to a wider radius if nothing is found), preferring the most recently captured image among the closest matches to avoid surfacing stale imagery in densely covered areas. Configurable in the Admin GUI (access token, search radius, fallback search radius).
- Admin: Kartinställningar - The per-map "Infobox" override field (`layerswitcher.options.baselayers[]`/`groups[].layers[].infobox`, which overrides a layer's own Infoklick template for that map only) now uses the same WYSIWYG editor and attribute picker as the layer-level Infoklick field, with an explanatory note about what it overrides. ### Changed

- Client: InfoDialog - Refactored to use LocalStorageHelper for visibility state management, enabling multiple named dialog instances with per-instance "show only once" tracking. Existing dialogs configured with `visibleAtStart` and `showOnlyOnce` will appear once more on next load, then persist correctly thereafter. No dialog content is lost; users require no action.

### Fixed

- Admin: WMTS-lager - The coordinate system and the tile grid origin are now derived correctly for services that do not look like Lantmäteriet's. `crsToEpsg` only recognized the URN form with a doubled colon, so Lantmäteriet's own `urn:ogc:def:crs:EPSG:6.3:3006` and swisstopo's `urn:ogc:def:crs:EPSG:2056` were stored verbatim as the layer's projection - a string no projection is registered under, which works only as long as the matrix set happens to share the map's projection. Four WMTS layers in the fork's own sandbox configs carry such a value. URNs from authorities other than EPSG are deliberately passed through, since OpenLayers resolves the OGC CRS84 URNs itself and rewriting them would produce a code nothing knows. The `TopLeftCorner` axis order was guessed from the sign of the first value, which is right for SWEREF 99 (northing first, positive) and Web Mercator (easting first, negative) and wrong for any easting-first CRS with positive eastings: swisstopo's EPSG:2056 publishes `2420000.0 1350000.0` and the guess swapped it, putting the tile grid origin somewhere else entirely. Axis order now comes from an explicit list of the coordinate systems Hajk supports, in the same spirit as the WMS form's `supportedProjections`, with the old sign heuristic kept as the fallback for anything unlisted so no service is worse off than before. Verified against live capabilities from Lantmäteriet, GeoWebCache and swisstopo: every Swedish and GeoServer grid produces exactly the same origin as before, and only EPSG:2056 changes. Confirmed in the Admin UI against Lantmäteriet's topowebb: selecting matrix set 3006 now fills Projektion with `EPSG:3006` rather than `urn:ogc:def:crs:EPSG:6.3:3006`, and Startkoordinater with `-1200000.000000 8500000.000000`, correctly swapped from the document's northing-first `8500000 -1200000`; matrix set 3857 fills `EPSG:3857` and leaves its origin unswapped.
- Admin: Capabilities-hantering - GetCapabilities documents are now parsed, validated and normalized in one shared module (`src/utils/CapabilitiesParser.js`) instead of twice, differently, in `layermanager.js`. Validation is the point of it: the only check used to be whether the root element was named `html`, so a service answering with an exception report was mistaken for a capabilities document with no layers in it - Trafikverket's NetInfo endpoint does exactly that, returning HTTP 200 and `serviceNotAvailable` to every WMS version, and Admin showed an empty layer list and no error. The root element must now be the document type that was asked for, an exception report is surfaced with the server's own words, and an HTTP 401 says the service wants credentials rather than blaming CORS. Normalization is the second half: repeatable elements are turned into arrays by element name at any depth, rather than at the four hardcoded paths X2JS was configured with, which stopped at depth two. Measured against live services, that leaves 60 of 60 layers at SCB, 14 of 14 at Naturvårdsregistret and 5 of 5 at RAÄ with a usable Stil dropdown, where before only the layers at depth two had one. Text nodes are unwrapped the same way everywhere, so namespace-prefixed values (`ows:Identifier`) and CDATA sections (an `Abstract` written as CDATA, which used to reach the form as an object) arrive as plain strings. Finally, the four WMS version requests no longer fail as a group: a service that answers some versions and rejects the rest is now usable, and the fetch fails only when every request failed. Verified against eight live documents from GeoServer, MapServer, GeoWebCache and two exception reports, checking both the parsed shape and the derivations the two forms run on it, and then in the Admin UI itself: an exception report now reports "Tjänsten svarade med ett felmeddelande: Missing LAYER parameter" and a WMS document pasted into the WMTS form is rejected by root element, where both used to be silent empty layer lists.
- Client: WMS `STYLES` is now derived from the same list as `LAYERS`, so the two correspond by construction. `ConfigMapper` built `LAYERS` from `layers` but `STYLES` by mapping `layersInfo` in its own order, and the two only line up by coincidence: `layersInfo` also carries one entry per sublayer of a GeoServer named group while `LAYERS` carries just the group, so every layer added after such a group was styled from the wrong slot. WMS binds STYLES positionally, and this was verified against a live GeoServer rather than assumed - a surplus of trailing entries is harmlessly ignored, but a style name landing on a layer that does not have it fails the whole GetMap with `No Style with name … found for LayerGroup …`, so every sublayer in that Hajk layer vanishes from the map at once instead of merely losing its styling. The style for each requested layer is now looked up by `id`, the same way `getLegendUrl` in the same file already did. Sublayer entries stay in `layersInfo` where captions and infoboxes need them; they simply no longer occupy positions in the request. No config migration needed.
- Admin: WMS-lager - `findInCapabilities` returned the wrong layer, or threw, for anything but a flat capabilities document. It used `find()` with the recursive call as its predicate, so a match below a group made `find()` return the group rather than the layer that matched, and the "Inställningar för lager" dialog - its only caller - filled the Stil dropdown from the parent group's styles. A group layer that is itself named and selectable could not be found at all, since any node with children returned early and its own `Name` was never compared. Worse, the recursion passed `Layer` on unnormalized: where a group has exactly one child, servers such as QGIS Server send it as an object rather than an array (the case behind #1182), and the next call died on `arrayToSearchIn.find is not a function` while rendering the dialog. The lookup is now an ordinary depth-first walk that checks each node before descending, normalizes children with `[].concat()`, and returns the matching layer itself. Verified by running the old and new implementations side by side over a synthetic tree covering nested layers, named groups, an unwrapped single child and a not-yet-loaded capabilities document - the last of which also threw before.
- Client: LayerSwitcher - The layer list filter now finds sublayers by the name they are actually shown under, and no longer risks crashing the layer tab. Matching is done twice - once in `LayersTab` to build the search index, which records a sublayer hit against its parent layer's id, and again in `GroupLayer` to decide which sublayers to display - and both looked only at `caption`. A sublayer without one is rendered by its technical layer name, so the text on screen existed in neither matcher and typing it returned no hits at all. Both paths now fall back to the layer name, the same way the label does. The index also dereferenced `layerInfo.layersInfo[sublayer].caption` unguarded and then called `toLocaleLowerCase()` on the result: `allSubLayers` comes from the WMS `LAYERS` parameter while `layersInfo` is a separate object in the layer config, and the two can disagree - `SubLayerItem` has always guarded against precisely that case - so a config where they did would throw on the first keystroke and take the whole layer tab down with it.
- Client + Admin: WMS-lager - Sublayers now get a display name of their own when they are added. Checking a layer under "Tillgängliga lager" created its entry with an empty `caption`, so a Hajk layer built from several WMS layers arrived in LayerSwitcher as a stack of nameless checkboxes, each of which had to be named by hand in "Inställningar för lager" - while the parallel "[Lägg till alla N sublager separat]" path had always pre-filled the name from the service's own title. Both paths now use the title from GetCapabilities. The title is taken from the rendered row rather than from `layerOpts`, which is only built for the top level of the capabilities tree and therefore has nothing to offer for a nested layer. The group's own Visningsnamn is deliberately left alone when more than one layer is checked, since that name is a choice rather than a copy. Existing configurations keep their empty captions - the pre-fill only applies when a layer is added - so the client now falls back to the layer's technical name instead of rendering a blank row, the same fallback infoclick has always had.
- Admin: WMS-lager - The "Koordinatsystem" list stayed empty for services whose root `Layer` element advertises exactly one `CRS`/`SRS`. The single value arrives as a string rather than an array, and `[...new Set(value)]` spread it character by character, so the form ended up testing "E", "P", "S", "G", ":" and so on against the supported-projection list, discarding all of them and logging one "Unsupported spatial reference system" line per character on every render. Normalizing with `[].concat()` first - the same thing the sibling branch for child layers already did - makes the projection appear and silences the noise. Services listing several root CRS were unaffected and still are.
- Backend: `App_Data` files that aren't map configurations are now refused up front with a 422 and an explanation, instead of failing deep inside the config pipeline as a bare 500. Nothing in a file name distinguishes a map config from a layers store, an unrelated document, or - by far the most common mistake - a saved response from `GET /config/<map>`, which nests the real config one level down under `mapConfig` and so looks convincing while being unreadable. The first code to touch such a file was `#removeUnusedLayersFromStore`, which died on `mapConfig.tools.find(...)` with "Cannot read properties of undefined (reading 'find')" - an error naming neither the file nor the problem. `getMapConfig` now checks that the parsed file is an object with a `map` object and a `tools` array, and throws a `MalformedConfigError` naming the file, the missing keys, the keys it did find, and the nested-response case specifically, including what to do about it. The message is logged server-side too, so it's findable without opening a browser console. This also stops one stray file from breaking `getUserSpecificMaps`, which loops over every map config and previously crashed on the first unreadable one rather than skipping it.
- Client: A map config that fails to load no longer silently opens a different map. Hajk retried against `appConfig.defaultMap` whenever the first request threw, and since the startup rework classifies any non-2xx response as a `ServiceUnavailableError`, a 500 on the requested map quietly loaded the default one instead - the user got a working map that simply wasn't the one they asked for, with nothing said anywhere. (Before that rework the same 500 fell through to a JSON parse failure and the generic error page, so this was a regression, not upstream behaviour.) The retry is now gone entirely rather than narrowed: a 404 is already fatal a few lines further down, a 5xx is a definitive answer about that particular map, and if the service is unreachable then asking it for a second map name cannot help either. A refused config (422) gets its own error page - "Den angivna filen är ingen korrekt kartfil" - carrying the backend's own explanation in the technical details, and offering "Öppna standardkartan" only when the map name came from the `m` parameter, since reloading cannot repair a bad file. Overridable from `appConfig.json` via the new `loadErrorInvalidMapFileTitle`/`Message` keys.
- Client: The "Trolig orsak" hint about `mapserviceBase` is no longer shown on 403, 404 and 422 error pages. Those statuses are Hajk's own backend answering, which proves the setting points where it should - naming it as the likely cause sent the reader after a setting that is demonstrably fine.
- Client: Disabled the upstream demo announcement ("Hi, this is **Hajk**!") that greeted every visitor to `map_1` and `simpleMapAndLayersConfig` on load. Set to `active: false` rather than deleted, so it remains as a working example of the `announcements` format - see `docs/admin-announcements.md`.
- Client: Startup errors now say what actually went wrong and offer a remedy that can work. Previously every failure that wasn't a 403 or 404 collapsed into "Ett fel har inträffat" with a single "Återställ applikationen" button that was hard-coded to `href="/"` - which broke sub-path deployments (the build sets `base: "./"`) and, for a server-side failure, just reloaded into the same error. The startup sequence now separates unreachable service, HTTP error, unparseable response and wrong-shaped config into distinct errors, each with its own message, and diagnoses the most common misconfiguration by comparing `mapserviceBase` against the address the page is served from: a `localhost` value on a non-local deployment, an http base under an https page, a port the client isn't on, or a cross-origin base, each named outright with a concrete suggested value. Buttons are now per-error ("Försök igen" for transient failures, "Öppna standardkartan" for a misspelled `m` parameter) and resolve against the app's own path instead of the domain root. An expandable "Teknisk information" section shows the requested URL, HTTP status, content type, resolved map name and `mapserviceBase`, with a copy button for support tickets. All texts remain overridable from `appConfig.json`, with new optional keys `loadErrorServiceUnavailableTitle`/`Message`, `loadErrorMalformedConfigTitle`/`Message`, `loadErrorRetryButtonText` and `loadErrorDefaultMapButtonText`.
